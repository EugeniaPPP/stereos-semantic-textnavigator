# PRD v0.2 — Semantic TextNavigator

## 1. Цель продукта

**Пользователь:** специалист по закупкам.

**Задача:** быстро определять действующие условия договоров поставки на выбранную дату без необходимости вручную сопоставлять договоры, допсоглашения и переписку.

**Ключевая ценность:** достоверные значения суммы и срока поставки с возможностью проверить каждое по исходному документу.

## 2. Пользовательский сценарий

1. Пользователь загружает несколько TXT-документов.
2. Выбирает дату проверки (по умолчанию 10.03.2026).
3. Система распознаёт документы, извлекает условия и связывает относящиеся к одному договору материалы.
4. Показывает таблицу действующих условий.
5. Пользователь открывает детали договора, видит источники и историю изменений.
6. При необходимости фильтрует договоры по сроку поставки и проверяет несогласованные изменения.
7. При изменении даты проверки или набора документов результаты пересчитываются.

## 3. Функциональные требования

### FR-1. Загрузка документов

- Множественная загрузка TXT через интерфейс.
- Анализ содержимого, независимо от имени файла и порядка загрузки.
- Поддержка новых договоров аналогичного формата.
- Ошибка одного документа не препятствует обработке остальных.
- При изменении набора файлов результаты обновляются без сохранения устаревших данных.

### FR-2. Распознавание и извлечение

Определять:

- Тип: договор, допсоглашение, проект изменения, письмо.
- Номер договора, поставщика.
- Общую согласованную стоимость в рублях.
- Срок поставки.
- Статус подписания и дату вступления в силу, если применимо.

Отличать общую стоимость от аванса и лимита бюджета, а срок поставки — от сроков оплаты и других дат.

Извлечённые поля должны сохраняться вместе с источниками.

### FR-3. Определение действующих условий

- Учитывать выбранную дату проверки.
- Исходный договор должен быть подписан к этой дате.
- Применять только допсоглашения, подписанные обеими сторонами и вступившие в силу.
- При нескольких изменениях применять их в порядке вступления в силу, если порядок однозначен.
- Обновлять только те поля, которые изменены соглашением.
- Не применять письма и неподписанные проекты.
- Если приоритет изменений нельзя установить — «Требует проверки».
- Если данных нет — «Нет данных».
- Если статус подписания или дата вступления в силу не установлены достоверно — не применять изменение автоматически, показывать предупреждение.

### FR-4. Неполный комплект документов

- Распознавать и обрабатывать дополнительные документы даже без исходного договора.
- Отображать их в разделе «Документы, требующие внимания».
- Не определять полный набор действующих условий договора только на основании допсоглашения.
- После загрузки исходного договора автоматически устанавливать связь и пересчитывать результат.
- Отдельно показывать документы неизвестного типа и документы, связь которых установить не удалось.

### FR-5. Проверяемость

Для каждого значения суммы и срока предоставлять:

- Имя файла.
- Точную цитату.
- Переход к соответствующему абзацу с подсветкой.
- Указание, каким документом установлено действующее значение.

При изменении условия показывать исходное и актуальное значения и основания изменений.

### FR-6. Интерфейс

**Главный экран:**

- Загрузка документов.
- Выбор даты проверки.
- Таблица: номер договора, поставщик, сумма, срок поставки, предупреждения.
- Фильтр по сроку поставки (раньше выбранной даты).

**Детали договора:**

- Действующие сумма и срок.
- Источники с навигацией к абзацам.
- Исходные и изменённые условия.
- Несогласованные предложения.

**Отдельный раздел:** документы, требующие внимания.

Произвольный чат не требуется.

## 4. Критерии приёмки

Для шести исходных файлов на 10.03.2026:

| Договор | Сумма | Срок |
|---|---|---|
| STN-101 | 1 380 000 ₽ | 30.04.2026 |
| STN-102 | 840 000 ₽ | 20.03.2026 |
| STN-103 | Нет данных | 30.04.2026 |

Обязательные проверки:

1. STN-101: применяется подписанное допсоглашение №1; проект №2 не применяется.
2. STN-102: письмо о переносе срока отображается отдельно; аванс не принимается за общую стоимость.
3. STN-103: бюджетный лимит не принимается за стоимость.
4. Фильтр «раньше 01.04.2026» возвращает STN-102 с предупреждением о предложенном изменении.
5. Изменение даты проверки влияет на применимость документов.
6. Изменение значения в TXT отражается в результате.
7. Новый договор того же формата обрабатывается без изменения кода.
8. Переименование файлов не меняет результат.
9. Отсутствующие или неоднозначные сведения не заменяются придуманными.
10. Допсоглашение без исходного договора отображается как обработанный, но не полностью разрешённый документ.
11. Все цитаты и переходы указывают на соответствующий исходный текст.

## 5. Технические и продуктовые ограничения

- Только TXT, без OCR и PDF/DOCX.
- LLM внутри приложения не используется.
- Извлечение: regex, контекстные правила и структурный анализ текста.
- Определение действующих условий: детерминированная бизнес-логика.
- ИИ-инструменты используются при разработке.
- Нет платных API, авторизации, постоянного хранилища и произвольного чата.
- Не гарантируется корректное извлечение из произвольных юридических формулировок.
- Прототип не проверяет подлинность подписей, а опирается на информацию из документов.
- Значения, номера договоров, имена файлов и ответы не хардкодятся в приложении.

## 6. Согласованные продуктовые решения

- **D1:** изменяемая дата проверки, по умолчанию 10.03.2026.
- **D2:** изменения применяются по дате вступления в силу; неоднозначные конфликты требуют проверки.
- **D3:** показывать исходное и действующее значение, без полной истории версий.
- **D4:** документы без исходного договора обрабатывать и отображать отдельно, без автоматического установления полного набора условий.
- **D5:** не использовать LLM в runtime; применять детерминированное извлечение с явно обозначенными ограничениями.
