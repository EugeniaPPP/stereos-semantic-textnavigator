# Архитектура

> Целевая архитектура прототипа. Готовность модулей отслеживается в `docs/PLAN.md`. Обоснования решений собраны в `README.md`, раздел «Архитектура, решения и компромиссы».

## Поток данных

```
[(filename, bytes)] ─ingest→ SourceDocument ─analyze→ DocumentAnalysis
  ─linking→ ContractGroup[] + AttentionItem[] ─resolve(D)→ ContractView[] → AnalysisResult → UI
```

Ядро — чистые детерминированные функции без streamlit. UI вызывает `pipeline.analyze(files, check_date)` на каждом rerun. Кэша нет, поэтому устаревших данных тоже нет.

## Принципы

1. Результат зависит только от содержимого файлов и даты проверки D. Идентичность документа — хэш содержимого; имя файла используется только для отображения.
2. Лучше «нет значения», чем неверное: `NO_DATA` / `NEEDS_REVIEW` с причиной и цитатой.
3. У каждого значения есть `Citation`; выполняется `text[start:end] == quote`.
4. Контекст правила — предложение. Слова-исключения (veto) проверяются в тексте предложения до значения.
5. Условия задаются реестром `TERM_REGISTRY`. Движок, резолвер и детали UI обходят его обобщённо.

## Модули

| Модуль | Ответственность |
|---|---|
| `model.py` | dataclasses и enums, без логики |
| `ingest.py` | декодирование (UTF-16 с BOM, UTF-8 с BOM и без, запасной вариант Windows-1251), CRLF→LF, NFC; отбраковка пустых и бинарных файлов (`ReadFailure`); абзацы с офсетами и номером пункта; предложения; `doc_id` |
| `patterns.py` | примитивы и парсеры: денежная сумма, дата ДД.ММ.ГГГГ (с валидацией), номер договора и его нормализация |
| `evidence.py` | `Citation` для фрагмента текста, обход предложений, сведение кандидатов в `Extraction` (FOUND / AMBIGUOUS / NOT_FOUND) |
| `meta.py` | тип документа, собственный номер, ссылка на договор, поставщик, дата документа, подпись, дата вступления в силу |
| `terms.py` | `Rule`, `FieldSpec`, `TERM_REGISTRY`, движок извлечения условий, пункты-изменения |
| `analyze.py` | `SourceDocument → DocumentAnalysis` |
| `linking.py` | дубликаты по `doc_id`; группировка по номеру договора; UNKNOWN_TYPE и UNLINKED в «Документы, требующие внимания»; порядок по номеру (натуральный), дате документа и `doc_id` |
| `resolve.py` | статусы договора и документов-изменений на дату, действующие значения полей, предупреждения (`Alert`), ORPHAN |
| `formatting.py` | формат сумм, дат, значений на дату (`value_text`: «Нет данных», «Требует проверки», «—») и названий документов — для сообщений ядра и UI |
| `pipeline.py` | `analyze(files, check_date) → AnalysisResult` (ошибки чтения и анализа → `READ_ERROR`); запросы для UI: `contracts_with_delivery_before(result, day)` (строго `<`, только `VALUE`; возвращает и число исключённых) и `unagreed_changes(view, field)` (`CHANGE_PROPOSAL`) |
| `ui/` | единственный пакет с импортом streamlit: `main_view.py` (главный экран, чистая функция `table_rows`), `details_view.py` (детали договора), `viewer.py` (`document_html` — чистая функция, `render_viewer`) |

## Модель данных

```python
Span(start, end)                                                        # [start, end) в SourceDocument.text
Paragraph(index, start, end, text, clause: str | None, sentences: tuple[Span, ...])
SourceDocument(doc_id, filename, text, encoding, paragraphs)            # doc_id = sha256(text)[:12]
ReadFailure(filename, reason)                                           # файл не прочитан, остальные обрабатываются
Citation(doc_id, filename, paragraph, start, end, quote, value_start, value_end)

DocType = CONTRACT | AMENDMENT | AMENDMENT_DRAFT | LETTER | UNKNOWN
Signature(status: SIGNED_BOTH | SIGNED_PARTIAL | NOT_SIGNED | UNKNOWN, date, citations)
Extraction(field, state: FOUND | NOT_FOUND | AMBIGUOUS | STATED_ABSENT | UNPARSED, value, citations)
DocumentMeta(doc_type, number, contract_number, supplier, doc_date, signature, effective_date)
ChangeClause(citation, target_clause: str | None, fields: tuple[str, ...])
DocumentAnalysis(source, meta: DocumentMeta, terms: dict[str, Extraction],
                 change_clauses: tuple[ChangeClause, ...])

ContractGroup(number, contracts: tuple[DocumentAnalysis, ...], changes: tuple[DocumentAnalysis, ...])
ChangeStatus = APPLIED | NOT_YET_EFFECTIVE | PROPOSAL | NEEDS_REVIEW
ChangeDoc(analysis, status, reason, changes: dict[str, Extraction])  # changes — затронутые поля
ContractStatus = IN_FORCE | NOT_IN_FORCE | NEEDS_REVIEW
TermValue(state: VALUE | NO_DATA | NEEDS_REVIEW | NOT_IN_FORCE, value, citations, source_doc_id, reason)
TermResolution(field, label, original, applied, effective, changed_by: tuple[doc_id, ...])
  # original — по договору; applied — после применённых ДС (последнее подтверждённое);
  # effective — что показывается на дату D
Alert(code: AlertCode, message, field, doc_id, citations)
ContractView(number, supplier, status, status_reason, contracts, terms, change_docs, alerts)
AttentionItem(reason: ORPHAN | UNLINKED | UNKNOWN_TYPE | READ_ERROR | DUPLICATE, message, filename,
              analysis, change: ChangeDoc | None)               # change — статус ORPHAN-документа
AnalysisResult(check_date, contracts, attention)

Rule(name, pattern)                                                     # шаблон с группой (?P<value>…)
FieldSpec(name, label, parse, rules, veto, mention, value_hint, absent, in_table)
TERM_REGISTRY = (TOTAL_COST, DELIVERY_DATE)
```

## Извлечение

- **Разбор текста:**
  - абзац — непустая строка без пробелов по краям;
  - номер пункта в начале строки («2.1.», «3.2.1», «1.») выделяется отдельно; число без точки («100 рублей») номером пункта не считается;
  - граница предложения: «.», «!», «?» или «…», затем возможные закрывающие кавычки или скобки, пробел и заглавная буква (возможно, после открывающей кавычки). Поэтому даты («15.04.2026») и ссылки («п. 2.1») не разрываются.
- **Примитивы** (`patterns.py`):
  - сумма — цифры с разделителями разрядов (пробел, NBSP), необязательные копейки и расшифровка в скобках, затем «рублей», «руб.» или «₽»; значение берётся только из цифр;
  - дата — «ДД.ММ.ГГГГ» или ««30» апреля 2026»; несуществующая дата («31.02.2026») значения не даёт;
  - номер — буквы и цифры с «-», «/», «.»; нормализация: верхний регистр, единый дефис.
- **Тип документа** определяется по заголовку (первая непустая строка), по приоритету:
  - «ПРОЕКТ ДОПОЛНИТЕЛЬНОГО СОГЛАШЕНИЯ» → `AMENDMENT_DRAFT`;
  - «ДОПОЛНИТЕЛЬНОЕ СОГЛАШЕНИЕ» или «ДОП. СОГЛАШЕНИЕ» → `AMENDMENT`;
  - «ДОГОВОР» → `CONTRACT`;
  - «ПИСЬМО» или строки «От:» и «Кому:» → `LETTER`;
  - иначе `UNKNOWN` (например, «ПРОЕКТ ДОГОВОРА», «АКТ»).
- **Номера и связывание.** Документы связываются по нормализованному номеру договора.
  - Собственный номер: у договора — «ДОГОВОР [ПОСТАВКИ] № X» в заголовке, у ДС и проекта — «СОГЛАШЕНИЕ № X».
  - Номер договора: у договора — собственный; у остальных — все упоминания «договор… [поставки] [№] X» в тексте. Без «№» токен должен содержать и букву, и цифру («STN-102»), поэтому «договора 2026 года» ссылкой не считается.
  - Несколько разных ссылок → `AMBIGUOUS`; в linking такой документ получает статус `UNLINKED`.
- **Поставщик** — предложение «Поставщик: …» или «Поставщик — …». Разные значения → `AMBIGUOUS`.
- **Дата документа** — строка «Дата[ уточнение]: <дата>», например «Дата проекта: 06.03.2026».
- **Подпись** определяется только по строкам «Статус[ уточнение]:», без них — `UNKNOWN`. Поэтому фразы о подписании других документов («после подписания дополнительного соглашения…») на статус не влияют.
  - «не подписан», «проект…», «на согласовании», «на подписании» → `NOT_SIGNED`.
  - «подписан(о) [только] поставщиком / покупателем / одной [из] сторон» → `SIGNED_PARTIAL`.
  - «подписан(о) [обеими] сторонами», если перед этим нет «не», → `SIGNED_BOTH`.
  - `SIGNED_BOTH` вместе с любым другим признаком → `UNKNOWN`. Частичная подпись важнее «не подписан»: «подписан поставщиком, покупателем не подписан» → `SIGNED_PARTIAL`.
  - Дата подписания — единственная дата в строках статуса (для `SIGNED_BOTH` и `SIGNED_PARTIAL`). Несколько разных дат → дата неизвестна.
- **Дата вступления в силу** — «<договор | соглашение | изменения> … вступает в силу [с] <дата>» или «… действует / применяется с <дата>».
  - Подлежащее обязательно, чтобы «Цена действует с …» не считалась датой вступления.
  - «Вступает в силу с момента (даты, дня) подписания» → дата подписания из строки статуса; если её нет, даты нет.
  - Несколько разных дат → `AMBIGUOUS`.
- **Условия** (`terms.py`) извлекаются по реестру `FieldSpec`; сам движок полей не знает.
  - **Где ищем.** В договоре — во всех предложениях. В ДС, проекте и письме — только в пунктах-изменениях (см. ниже); значения вне них («Общая стоимость договора составляет …») игнорируются.
  - **Правила** (`Rule`) применяются к предложению по порядку, от специфичных к общим; срабатывает первое подошедшее.
    - Сумма: «изменить … на X»; «увеличить / уменьшить … до X»; «<стоимость | цена | сумма> [договора | поставки | товара] <составляет | равна | — | :> X»; «на [общую] сумму X».
    - Срок: «перенести / изменить / продлить срок поставки [с D1] на / до D2» (значение — D2); «срок поставки переносится на D»; «поставить / поставка / осуществить поставку … не позднее / до / по D»; «срок поставки: D».
  - **Слова-исключения** (`veto`) отменяют совпадение, если стоят в предложении до конца значения. Так «Аванс … от общей стоимости составляет X» отбрасывается, а «Общая стоимость составляет X, включая аванс Y» — нет.
    - Для суммы: аванс, предоплата, лимит, бюджет, неустойка, штраф, пени, задаток, обеспечение.
    - Для срока: оплата, платёж, приёмка, неустойка, гарантийный, аванс, претензия, «договор действует / вступает», «срок действия», «вступает в силу».
  - **`UNPARSED`** — поле упомянуто (`mention`) и есть похожий на значение фрагмент (`value_hint`: «руб», дата, «в течение N дней»), но ни одно правило не дало значения. Примеры: «один миллион рублей», «в течение 30 дней», «31.02.2026», «увеличить на 100 000 рублей».
  - **Итог по договору:** значения есть → `FOUND` или `AMBIGUOUS` (разные значения); иначе `UNPARSED`; иначе `STATED_ABSENT` («не указано», «не установлено», «определяется спецификацией»); иначе `NOT_FOUND`.
  - **Итог по документу-изменению:** поле упомянуто в пункте-изменении без значения → `UNPARSED`. Разные значения или значение вместе с нераспознанным изменением того же поля → `AMBIGUOUS`.
- **Пункты-изменения (`ChangeClause`)** — абзацы ДС, проекта или письма с глаголом изменения: «изложить», «изменить / изменяется», «перенести / переносится», «увеличить», «уменьшить», «заменить», «продлить», «установить», «дополнить», «исключить» (не после «не»).
  - Существительные («изменения», «без изменений») намерением изменения не считаются.
  - Заголовок и служебные строки («Дата:», «Статус:», «Тема:», «Покупатель:» …) пропускаются.
  - Для пункта фиксируются целевой пункт договора («Пункт 2.1 …» → «2.1») и затронутые поля — те, где найдено значение или поле упомянуто.

## Статусы на дату проверки D

Все границы включительно (≤ D).

### Договор

- `IN_FORCE` — `SIGNED_BOTH`, подписан ≤ D, и дата вступления в силу не указана либо она ≤ D.
- `NOT_IN_FORCE` с причиной: «подписан после даты проверки», «подписан, вступает в силу <дата>» или «подписан одной стороной». Поля получают `effective = NOT_IN_FORCE`: в таблице «—», в фильтр по сроку договор не попадает. Значения из текста остаются в `applied` для деталей.
- `NEEDS_REVIEW` в одном из случаев (поля получают `effective = NEEDS_REVIEW`):
  - подпись `UNKNOWN`;
  - дата подписания неизвестна или дата вступления в силу неоднозначна;
  - тип «договор» при статусе `NOT_SIGNED` или «проект» (противоречие);
  - загружено несколько разных договоров с одним номером.

### Документ-изменение

| Тип \ подпись | SIGNED_BOTH | SIGNED_PARTIAL | NOT_SIGNED | UNKNOWN |
|---|---|---|---|---|
| `AMENDMENT` | подписано ≤ D и вступило ≤ D → `APPLIED`; подписано или вступает позже D → `NOT_YET_EFFECTIVE`; дата подписания или вступления неизвестна либо неоднозначна → `NEEDS_REVIEW` | `PROPOSAL` | `NEEDS_REVIEW` (противоречие тип ↔ статус) | `NEEDS_REVIEW` |
| `AMENDMENT_DRAFT` | `NEEDS_REVIEW` (противоречие) | `PROPOSAL` | `PROPOSAL` | `PROPOSAL` |
| `LETTER` | `PROPOSAL` (статус подписи не учитывается) | | | |

### Поля

Правила одинаковы для всех полей реестра.

1. Исходное значение берётся из договора.
2. Затем применяются изменения со статусом `APPLIED` — по дате вступления в силу (затем по дате подписания и `doc_id`), а не по номеру ДС или порядку файлов. Обновляются только затронутые поля:
   - `FOUND` → новое значение; источником становится это ДС;
   - `AMBIGUOUS`, `UNPARSED` или ДС меняет пункт договора, где было найдено поле, но значения не содержит → `NEEDS_REVIEW`. Более позднее применённое ДС с чётким значением перекрывает это состояние; история сохраняется;
   - одна дата вступления и разные значения поля → `NEEDS_REVIEW` без тай-брейков.
3. Документ со статусом `NEEDS_REVIEW`, затрагивающий поле, переводит `effective` в `NEEDS_REVIEW`. Изменение не применяется: последнее подтверждённое значение остаётся в `applied`.
4. `NOT_YET_EFFECTIVE` и `PROPOSAL` значения не меняют.
5. Документы с датой позже D видны в деталях, но на таблицу не влияют. Исключение — подписанные ДС: для них решают даты подписания и вступления в силу.
6. ДС без договора → `ORPHAN` в разделе «Документы, требующие внимания»: документ обработан и получил `ChangeStatus`, но условия не определяются. Когда договор загружен, связь восстанавливается при пересчёте.

### Предупреждения (`Alert`)

| Код | Когда |
|---|---|
| `CONTRACT_NOT_IN_FORCE`, `CONTRACT_NEEDS_REVIEW` | статус договора не `IN_FORCE` (причина — в сообщении) |
| `CHANGE_PENDING` | подписанное ДС ещё не действует — по одному на затронутое поле, с полем и значением |
| `CHANGE_PROPOSAL` | несогласованное предложение (письмо, проект, подписано одной стороной) — по одному на затронутое поле |
| `CHANGE_NEEDS_REVIEW` | изменение со статусом `NEEDS_REVIEW` не применено |
| `FIELD_NEEDS_REVIEW` | `effective = NEEDS_REVIEW` у действующего договора (причина — в сообщении) |
| `UNRECOGNIZED_CHANGE` | пункт-изменение применённого ДС без известных полей, не переписывающий пункт договора с известным полем |
| `EMPTY_AMENDMENT` | применённое ДС без единого пункта-изменения |
| `SUPPLIER_MISMATCH` | поставщик в документе-изменении не совпадает с поставщиком договора |

Колонка «несогласованные изменения» и вопрос «есть ли несогласованные изменения срока» строятся по `CHANGE_PROPOSAL` и `CHANGE_PENDING` с нужным `field`.

## UI

- **Главный экран** (`ui/main_view.py`, вход — `app.py`):
  - загрузка TXT и дата проверки (по умолчанию 10.03.2026); на каждом rerun вызывается `pipeline.analyze`;
  - статичная таблица `st.table`: номер, поставщик, колонки полей реестра с `in_table=True`, «Несогласованные изменения» (по документу: «Письмо от …: срок поставки → …»), «Статус и предупреждения» (сообщения `Alert`, кроме `CHANGE_PROPOSAL`);
  - значения: `VALUE` — формат суммы или даты, `NO_DATA` — «Нет данных», `NEEDS_REVIEW` — «Требует проверки» (выделено фоном), `NOT_IN_FORCE` — «—»; пробелы в ячейках неразрывные, чтобы суммы не переносились;
  - фильтр: флажок «Только со сроком поставки раньше даты» и дата (по умолчанию = D) → `contracts_with_delivery_before`, строго `<`; число исключённых договоров показано подписью.
- **Детали договора** (`ui/details_view.py`): выбор договора; слева — прокручиваемая панель фиксированной высоты, справа — просмотрщик, поэтому исходный текст всегда рядом с цитатой.
  - статус договора и причина;
  - по каждому полю реестра: значение на дату, основание (документ и файл), при изменении — значение по договору; для «Нет данных» и «Требует проверки» — причина и последнее подтверждённое значение;
  - цитаты: предложение целиком, значение выделено, место — «`файл`, абзац N, п. X»; у каждой цитаты кнопка «Показать в документе»;
  - четыре группы изменений: «Применённые», «Подписанные, но не вступившие в силу», «Несогласованные предложения», «Требуют проверки»; у неприменённых — цитаты изменённых значений;
  - прочие предупреждения: нераспознанные изменения, ДС без изменений, несовпадение поставщика.
- **Просмотрщик** (`ui/viewer.py`): весь документ в `st.iframe` (замена устаревшего `components.html`); целевой абзац подсвечен, цитата затонирована, значение — `<mark>`, скрипт прокручивает к абзацу. Весь текст документа экранируется `html.escape`: загруженный файл не может добавить разметку или скрипт. Выбранная цитата хранится в `st.session_state` отдельно для каждого договора; по умолчанию — цитата первого поля.
- **Документы, требующие внимания:** ORPHAN («обработан, не разрешён»), UNLINKED, UNKNOWN_TYPE, READ_ERROR, DUPLICATE.
- **`STN_PRELOAD_DIR`** — dev-переменная окружения. Она подгружает `*.txt` из каталога как загруженные файлы и нужна для демо, AppTest и проверки в браузере.

## Как добавить извлекаемое поле

1. Описать `FieldSpec` в `textnav/terms.py`: `name`, `label`, `parse`, `rules` (сначала формулировки изменения, затем утверждения), `veto`, `mention`, `value_hint`, `absent`, `in_table`. Добавить его в `TERM_REGISTRY`.
2. Написать сниппет-тесты: значение, дистракторы, изменение в ДС, отсутствие.
3. Движок, резолвер и детали UI подхватят поле автоматически. Колонка в таблице появится при `in_table=True`.
