# Архитектура

> Целевая архитектура прототипа. Готовность модулей отслеживается в `docs/PLAN.md`. Обоснования решений собраны в `README.md`, раздел «Архитектура, решения и компромиссы».

## Поток данных

```
[(filename, bytes)] ─ingest→ SourceDocument ─analyze→ DocumentAnalysis
  ─linking→ ContractGroup[] + AttentionItem[] ─resolve(D)→ ContractView[] → AnalysisResult → UI
```

Ядро — чистые детерминированные функции без streamlit. UI вызывает `pipeline.analyze(files, check_date)` на каждом rerun. Кэша нет, поэтому устаревших данных тоже нет.

## Принципы

1. Результат зависит только от содержимого файлов и даты проверки D. Идентичность документа — хэш содержимого; имя файла используется только для отображения.
2. Лучше «нет значения», чем неверное: `NO_DATA` / `NEEDS_REVIEW` с причиной и цитатой.
3. У каждого значения есть `Citation`; выполняется `text[start:end] == quote`.
4. Контекст правила — предложение. Слова-исключения (veto) проверяются в том же предложении.
5. Условия задаются реестром `TERM_REGISTRY`. Движок, резолвер и детали UI обходят его обобщённо.

## Модули

| Модуль | Ответственность |
|---|---|
| `model.py` | dataclasses и enums, без логики |
| `ingest.py` | декодирование (UTF-16 с BOM, UTF-8 с BOM и без, запасной вариант Windows-1251), CRLF→LF, NFC; отбраковка пустых и бинарных файлов (`ReadFailure`); абзацы с офсетами и номером пункта; предложения; `doc_id` |
| `patterns.py` | примитивы и парсеры: денежная сумма, дата ДД.ММ.ГГГГ (с валидацией), номер договора и его нормализация |
| `evidence.py` | `Citation` для фрагмента текста, обход предложений, сведение кандидатов в `Extraction` (FOUND / AMBIGUOUS / NOT_FOUND) |
| `meta.py` | тип документа, собственный номер, ссылка на договор, поставщик, дата документа, подпись, дата вступления в силу |
| `terms.py` | `Rule`, `FieldSpec`, `TERM_REGISTRY`, движок извлечения условий, пункты-изменения |
| `analyze.py` | `SourceDocument → DocumentAnalysis` |
| `linking.py` | группировка документов по договору, дубликаты, «Документы, требующие внимания» |
| `resolve.py` | статусы договора и документов-изменений на дату, действующие значения, предупреждения |
| `pipeline.py` | `analyze(files, check_date) → AnalysisResult`, детерминированная сортировка |
| `ui/` | `formatting.py` (формат сумм, дат, статусов), `main_view.py`, `details_view.py`, `viewer.py` |

## Модель данных

```python
Span(start, end)                                                        # [start, end) в SourceDocument.text
Paragraph(index, start, end, text, clause: str | None, sentences: tuple[Span, ...])
SourceDocument(doc_id, filename, text, encoding, paragraphs)            # doc_id = sha256(text)[:12]
ReadFailure(filename, reason)                                           # файл не прочитан, остальные обрабатываются
Citation(doc_id, filename, paragraph, start, end, quote, value_start, value_end)

DocType = CONTRACT | AMENDMENT | AMENDMENT_DRAFT | LETTER | UNKNOWN
Signature(status: SIGNED_BOTH | SIGNED_PARTIAL | NOT_SIGNED | UNKNOWN, date, citations)
Extraction(field, state: FOUND | NOT_FOUND | AMBIGUOUS | STATED_ABSENT | UNPARSED, value, citations)
DocumentMeta(doc_type, number, contract_number, supplier, doc_date, signature, effective_date)
ChangeClause(citation, target_clause: str | None, fields: tuple[str, ...])
DocumentAnalysis(source, meta: DocumentMeta, terms: dict[str, Extraction],
                 change_clauses: list[ChangeClause], issues)

ChangeStatus = APPLIED | NOT_YET_EFFECTIVE | PROPOSAL | NEEDS_REVIEW
ChangeDoc(doc, status, reason, changes: dict[str, Extraction])
ContractStatus = IN_FORCE | NOT_IN_FORCE | NEEDS_REVIEW
TermValue(state: VALUE | NO_DATA | NEEDS_REVIEW, value, citations, set_by_doc_id, reason)
TermResolution(field, original: TermValue, effective: TermValue, history)
ContractView(number, supplier, status, status_reason, terms, change_docs, warnings, documents)
AttentionItem(doc, reason: ORPHAN | UNLINKED | UNKNOWN_TYPE | READ_ERROR | DUPLICATE | CONFLICTING_CONTRACT)
AnalysisResult(check_date, contracts, attention)

Rule(name, pattern /(?P<value>…)/ [+ (?P<old>…)], kind: STATEMENT | CHANGE)
FieldSpec(name, label, parse, rules, veto, mention, absent_markers, in_table)
TERM_REGISTRY = (TOTAL_COST, DELIVERY_DATE)
```

## Извлечение

- **Разбор текста:**
  - абзац — непустая строка без пробелов по краям;
  - номер пункта в начале строки («2.1.», «3.2.1», «1.») выделяется отдельно; число без точки («100 рублей») номером пункта не считается;
  - граница предложения: «.», «!», «?» или «…», затем возможные закрывающие кавычки или скобки, пробел и заглавная буква (возможно, после открывающей кавычки). Поэтому даты («15.04.2026») и ссылки («п. 2.1») не разрываются.
- **Примитивы** (`patterns.py`):
  - сумма — цифры с разделителями разрядов (пробел, NBSP), необязательные копейки и расшифровка в скобках, затем «рублей», «руб.» или «₽»; значение берётся только из цифр;
  - дата — «ДД.ММ.ГГГГ» или ««30» апреля 2026»; несуществующая дата («31.02.2026») значения не даёт;
  - номер — буквы и цифры с «-», «/», «.»; нормализация: верхний регистр, единый дефис.
- **Тип документа** определяется по заголовку (первая непустая строка), по приоритету:
  - «ПРОЕКТ ДОПОЛНИТЕЛЬНОГО СОГЛАШЕНИЯ» → `AMENDMENT_DRAFT`;
  - «ДОПОЛНИТЕЛЬНОЕ СОГЛАШЕНИЕ» или «ДОП. СОГЛАШЕНИЕ» → `AMENDMENT`;
  - «ДОГОВОР» → `CONTRACT`;
  - «ПИСЬМО» или строки «От:» и «Кому:» → `LETTER`;
  - иначе `UNKNOWN` (например, «ПРОЕКТ ДОГОВОРА», «АКТ»).
- **Номера и связывание.** Документы связываются по нормализованному номеру договора.
  - Собственный номер: у договора — «ДОГОВОР [ПОСТАВКИ] № X» в заголовке, у ДС и проекта — «СОГЛАШЕНИЕ № X».
  - Номер договора: у договора — собственный; у остальных — все упоминания «договор… [поставки] [№] X» в тексте. Без «№» токен должен содержать и букву, и цифру («STN-102»), поэтому «договора 2026 года» ссылкой не считается.
  - Несколько разных ссылок → `AMBIGUOUS`; в linking такой документ получает статус `UNLINKED`.
- **Поставщик** — предложение «Поставщик: …» или «Поставщик — …». Разные значения → `AMBIGUOUS`.
- **Дата документа** — строка «Дата[ уточнение]: <дата>», например «Дата проекта: 06.03.2026».
- **Подпись** определяется только по строкам «Статус[ уточнение]:», без них — `UNKNOWN`. Поэтому фразы о подписании других документов («после подписания дополнительного соглашения…») на статус не влияют.
  - «не подписан», «проект…», «на согласовании», «на подписании» → `NOT_SIGNED`.
  - «подписан(о) [только] поставщиком / покупателем / одной [из] сторон» → `SIGNED_PARTIAL`.
  - «подписан(о) [обеими] сторонами», если перед этим нет «не», → `SIGNED_BOTH`.
  - `SIGNED_BOTH` вместе с любым другим признаком → `UNKNOWN`. Частичная подпись важнее «не подписан»: «подписан поставщиком, покупателем не подписан» → `SIGNED_PARTIAL`.
  - Дата подписания — единственная дата в строках статуса (для `SIGNED_BOTH` и `SIGNED_PARTIAL`). Несколько разных дат → дата неизвестна.
- **Дата вступления в силу** — «<договор | соглашение | изменения> … вступает в силу [с] <дата>» или «… действует / применяется с <дата>».
  - Подлежащее обязательно, чтобы «Цена действует с …» не считалась датой вступления.
  - «С момента подписания» даты не даёт — используется дата подписания.
  - Несколько разных дат → `AMBIGUOUS`.
- **Условия.** Правила применяются к предложению, от специфичных к общим:
  - сначала `CHANGE`: «с X на Y» (значение — Y), «изменить … на Y»;
  - затем `STATEMENT`: «стоимость … составляет X», «поставить … не позднее D»;
  - veto для суммы: аванс, лимит, бюджет, неустойка; veto для срока: оплата, приёмка, платёж;
  - «не указано» или «не установлено» рядом с упоминанием поля → `STATED_ABSENT` (цитата для «Нет данных»);
  - разные значения одного поля в документе → `AMBIGUOUS`.
- **Пункты-изменения (`ChangeClause`)** ищутся в ДС, проектах и письмах. Это предложения с намерением изменения: «изложить в редакции», «изменить», «перенести», «увеличить», «заменить» и т. п.; формулировки «без изменений» исключаются. Для каждого пункта фиксируются целевой пункт договора («Пункт 2.1») и найденные поля. Поле упомянуто (`FieldSpec.mention`), но значение не извлечено → `UNPARSED`.

## Статусы на дату проверки D

Все границы включительно (≤ D).

### Договор

- `IN_FORCE` — `SIGNED_BOTH`, подписан ≤ D, и дата вступления в силу не указана либо она ≤ D.
- `NOT_IN_FORCE` с причиной: «подписан после даты проверки», «подписан, вступает в силу <дата>» или «подписан одной стороной». Строка остаётся в таблице, сумма и срок показываются как «—», в фильтр по сроку договор не попадает.
- `NEEDS_REVIEW` в одном из случаев:
  - подпись `UNKNOWN`;
  - дата подписания или вступления в силу неизвестна либо неоднозначна;
  - тип «договор» при статусе `NOT_SIGNED` или «проект» (противоречие);
  - загружены конфликтующие дубликаты.

### Документ-изменение

| Тип \ подпись | SIGNED_BOTH | SIGNED_PARTIAL | NOT_SIGNED | UNKNOWN |
|---|---|---|---|---|
| `AMENDMENT` | подписано ≤ D и вступило ≤ D → `APPLIED`; подписано или вступает позже D → `NOT_YET_EFFECTIVE`; дата подписания или вступления неизвестна → `NEEDS_REVIEW` | `PROPOSAL` | `NEEDS_REVIEW` (противоречие тип ↔ статус) | `NEEDS_REVIEW` |
| `AMENDMENT_DRAFT` | `NEEDS_REVIEW` (противоречие) | `PROPOSAL` | `PROPOSAL` | `PROPOSAL` |
| `LETTER` | `PROPOSAL` (статус подписи не учитывается) | | | |

### Поля

Правила одинаковы для всех полей реестра.

1. Исходное значение берётся из договора.
2. Затем по порядку дат вступления применяются изменения со статусом `APPLIED`. Обновляются только затронутые поля:
   - `FOUND` → новое значение; источником становится это ДС;
   - `AMBIGUOUS`, `UNPARSED` или ДС меняет пункт договора, где было найдено поле, но значения не содержит → `NEEDS_REVIEW`. Более позднее применённое ДС с чётким значением перекрывает это состояние; история сохраняется;
   - одна дата вступления и разные значения поля → `NEEDS_REVIEW` без тай-брейков.
3. Документ со статусом `NEEDS_REVIEW`, затрагивающий поле, переводит поле в `NEEDS_REVIEW`. Изменение не применяется. В деталях показаны последнее подтверждённое значение и неподтверждённое.
4. `NOT_YET_EFFECTIVE` и `PROPOSAL` значения не меняют и дают разные предупреждения: «Подписано, вступает в силу <дата>» и «Несогласованное предложение».
5. Документы с датой позже D видны в деталях, но на таблицу не влияют. Исключение — подписанные ДС: для них решают даты подписания и вступления в силу.
6. Пункт-изменение применённого ДС, в котором нет известных полей → предупреждение «нераспознанное изменение п. N» на уровне договора.
7. ДС без договора → `ORPHAN` в разделе «Документы, требующие внимания», условия не определяются. Когда договор загружен, связь восстанавливается при пересчёте.

## UI

- **Главный экран:**
  - загрузка TXT и дата проверки (по умолчанию 10.03.2026);
  - таблица: номер, поставщик, сумма, срок, несогласованные изменения по полям, статус и предупреждения;
  - фильтр «срок поставки раньше <дата>»: строгое `<`, по умолчанию дата = D; договоры без достоверного срока исключаются, их число показано подписью.
- **Детали договора:**
  - действующие значения и документ-основание; исходное → действующее значение;
  - четыре группы изменений: «Применённые», «Подписанные, не вступившие в силу», «Несогласованные предложения», «Требуют проверки»;
  - у каждого значения кнопка «Показать в документе».
- **Просмотрщик:** весь документ в `components.html`, целевой абзац подсвечен, значение обёрнуто в `<mark>`, автопрокрутка. Текст экранируется (`html.escape`).
- **Документы, требующие внимания:** ORPHAN («обработан, не разрешён»), UNLINKED, UNKNOWN_TYPE, READ_ERROR, DUPLICATE.
- **`STN_PRELOAD_DIR`** — dev-переменная окружения. Она подгружает `*.txt` из каталога как загруженные файлы и нужна для демо, AppTest и проверки в браузере.

## Как добавить извлекаемое поле

1. Описать `FieldSpec` в `textnav/terms.py`: `name`, `label`, `parse`, правила `STATEMENT` и `CHANGE`, `veto`, `mention`, `absent_markers`, `in_table`. Добавить его в `TERM_REGISTRY`.
2. Написать сниппет-тесты: значение, дистракторы, изменение в ДС, отсутствие.
3. Движок, резолвер и детали UI подхватят поле автоматически. Колонка в таблице появится при `in_table=True`.
