# Semantic TextNavigator

Прототип для специалиста по закупкам. По загруженным TXT-документам (договоры поставки, допсоглашения, проекты изменений, письма) он показывает сумму и срок поставки, действующие на выбранную дату. Каждое значение подтверждено точной цитатой с переходом к исходному абзацу.

- Требования: [`docs/PRD.md`](docs/PRD.md)
- Исходное задание: [`docs/TASK.md`](docs/TASK.md)
- Архитектура: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)
- План и журнал разработки: [`docs/PLAN.md`](docs/PLAN.md)

> **Статус:** в разработке: ядро и главный экран готовы (итерация 6), детали договора и переход к цитатам — следующий этап. Состояние итераций смотрите в `docs/PLAN.md`.

## 1. Запуск и тесты

Нужен Python 3.12. На macOS его можно поставить командой `brew install python@3.12`.

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/streamlit run app.py
```

Откройте http://localhost:8501, загрузите TXT-файлы из папки `documents/` и выберите дату проверки (по умолчанию 10.03.2026).

Для демонстрации файлы можно подгрузить автоматически — переменная `STN_PRELOAD_DIR` добавляет все `*.txt` из папки к загруженным:

```bash
STN_PRELOAD_DIR=documents .venv/bin/streamlit run app.py
```

Проверки:

```bash
.venv/bin/pytest
.venv/bin/ruff check . && .venv/bin/ruff format --check .
```

**Зависимости:**
- `requirements.txt` — полный пиннинг runtime-зависимостей. Именно этот файл устанавливает Streamlit Community Cloud.
- `requirements-dev.txt` — runtime + pytest и ruff.
- Чтобы обновить пины: в чистом venv на Python 3.12 установите нужную версию `streamlit` и замените тело `requirements.txt` выводом `pip freeze`, сохранив комментарий-шапку.

**Streamlit Community Cloud** (опционально): репозиторий, ветка `main`, файл `app.py`, Python 3.12. Версия Python выбирается при деплое в Advanced settings.

## 2. Как получить ответы на 4 вопроса задания

Загрузите все файлы из `documents/` и оставьте дату проверки 10.03.2026. В коде ответов нет — приложение вычисляет их из загруженных текстов.

| Вопрос | Где смотреть | Ожидаемый ответ |
|---|---|---|
| 1. Какой срок поставки действует по STN-101 на 10.03.2026? | строка STN-101, колонка «Срок поставки» | 30.04.2026 — установлен допсоглашением № 1; проект допсоглашения № 2 виден в колонке «Несогласованные изменения» и не применяется |
| 2. Какова сумма STN-102? | строка STN-102, колонка «Сумма» | 840 000 ₽; аванс 252 000 ₽ не принимается за общую стоимость |
| 3. Какова сумма STN-103? | строка STN-103, колонка «Сумма» | Нет данных; лимит бюджета 600 000 ₽ не принимается за стоимость договора |
| 4. По каким договорам поставка раньше 01.04.2026 и есть ли несогласованные изменения срока? | отметьте «Только со сроком поставки раньше даты», укажите 01.04.2026, смотрите колонку «Несогласованные изменения» | STN-102 (20.03.2026); письмо от 05.03.2026 предлагает перенос на 27.03.2026, изменение не согласовано |

Если сменить дату проверки, таблица пересчитается: например, на 28.02.2026 у STN-101 будут 1 200 000 ₽ и 15.04.2026, а допсоглашение № 1 — «подписано после даты проверки».

## 3. Продуктовая записка

_Черновик, финализируется на итерации 8._

**5 вопросов клиенту**
1. Если стоимость задана в приложении или спецификации (как в STN-103), нужно ли загружать приложения и считать стоимость по ним?
2. Кто принимает решение по позициям «Требует проверки» и какой приоритет действует при конфликте изменений, например у двух ДС с одной датой вступления в силу?
3. Где взять достоверный статус подписания: в тексте документа, в ЭДО или в учётной системе?
4. Какие условия, кроме суммы и срока, критичны для проверки: поэтапные сроки, неустойка, условия оплаты, валюта и НДС?
5. Откуда и в каком объёме поступают документы (СЭД, почта, сканы) и нужна ли выгрузка результата (Excel, 1С)?

**Допущения**
- Статус подписания и даты в тексте считаются достоверными. Подлинность подписей не проверяется.
- Даты записаны как «ДД.ММ.ГГГГ» или «30 апреля 2026», суммы — цифрами в рублях.
- У договора одна общая стоимость и один срок поставки.
- Номер договора уникален и одинаково записан во всех связанных документах.
- Кодировки: UTF-8, UTF-16 с BOM, запасной вариант Windows-1251. Один абзац — одна строка.
- Даты подписания и вступления в силу сравниваются с датой проверки включительно.

**2 метрики**
1. **Доля неверных «уверенных» значений** на размеченном наборе. Считаются случаи, когда показано значение (а не «Нет данных» или «Требует проверки») и оно расходится с эталоном. Цель — 0%. Это главная метрика доверия.
2. **Покрытие** — доля договоров, у которых сумма и срок определены автоматически, без «Требует проверки». Показывает экономию ручной работы. Повышать её допустимо только без ухудшения метрики 1.

## 4. Архитектура, решения и компромиссы

Конвейер: TXT → разбор на абзацы и предложения → извлечение метаданных и условий по правилам → связывание документов по номеру договора → детерминированное определение действующих условий на дату → интерфейс Streamlit. Подробности — в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

**Почему правила, а не LLM, и где границы подхода.** Правила детерминированы и проверяемы: каждое значение привязано к цитате. Они не галлюцинируют, бесплатны и работают офлайн. Подход надёжен на документах с известной структурой и формулировками. Если формулировка незнакома, система показывает «Требует проверки» или «Нет данных», а не догадку. Для произвольных юридических текстов этого недостаточно (см. «Следующие улучшения»).

**Ключевые решения**

| Решение | Почему | Компромисс |
|---|---|---|
| Контекст правила — предложение; слова-исключения (аванс, лимит, оплата, приёмка) проверяются в тексте до значения | Отличает общую стоимость от аванса и лимита, срок поставки — от сроков оплаты и приёмки | Сложные предложения с несколькими условиями требуют отдельных правил |
| Абзац = непустая строка | Совпадает с форматом документов, офсеты для цитат простые и точные | Файлы с жёстким переносом строк порвут предложения |
| Статус подписи — только из строки «Статус:» | Упоминания подписания других документов (ДС в тексте договора, подписание в письме) не влияют на статус документа | Документ без такой строки получает «Требует проверки» |
| Идентичность документа — хэш содержимого | Переименование и порядок загрузки не влияют на результат | — |
| Пересчёт на каждом действии, без кэша | Нет устаревших данных после смены файлов или даты | Не масштабируется на тысячи документов (см. раздел 5) |
| Даты включительно; договор действует с max(подписание, вступление в силу) | Однозначное правило | Ретроактивные оговорки не моделируются |
| ДС применяются по дате вступления в силу, а не по номеру или порядку файлов | Так требует PRD; переименование и порядок загрузки не влияют | — |
| ДС без даты вступления в силу → «Требует проверки» («с момента подписания» = дата подписания) | PRD FR-3: дата вступления должна быть установлена достоверно | ДС, где дата вступления просто не указана, не применяются автоматически |
| Подписанное, но не вступившее в силу ДС отделено от несогласованных предложений | Разный юридический статус: первое вступит в силу само, второе — нет | — |
| Документ, датированный позже даты проверки, не даёт предупреждений в таблице (кроме подписанных ДС) | На дату проверки его ещё не было | Виден только в деталях |
| Одна дата вступления и разные значения → «Требует проверки» | PRD D2: неоднозначный приоритет не угадывается | Чаще нужна ручная проверка |
| Противоречие «тип документа ↔ статус подписи» → «Требует проверки»; ДС, подписанное одной стороной, → несогласованное предложение | Изменение не применяется без достоверного основания | Консервативность снижает покрытие (метрика 2) ради точности (метрика 1) |
| В ДС, проекте и письме значения ищутся только в пунктах-изменениях; поле упомянуто, а значение не распознано → «нераспознано» | Изменение не теряется молча | Перефразированные изменения чаще требуют ручной проверки |
| Нераспознанное изменение суммы или срока в действующем ДС → «Требует проверки» | Нельзя уверенно показывать прежнее значение | — |
| Новое поле — запись в реестре `FieldSpec` | Расширение без переработки движка | Правила для нового поля всё равно нужно писать и тестировать |
| Streamlit; просмотрщик документа — во встроенном iframe | Быстрый рабочий UI без фронтенд-сборки | Навигация к абзацу работает внутри просмотрщика, а не по странице |
| Таблица договоров — статичная (`st.table`), а не интерактивная сетка | Каждое предупреждение читается целиком, без обрезки; ненадёжные значения выделены прямо в ячейке | Нет сортировки по колонкам; при сотнях договоров понадобится сетка с пагинацией |
| Python 3.12, `requirements.txt` с пинами, плоская раскладка пакета | Воспроизводимость; совместимость со Streamlit Community Cloud (3.12 там по умолчанию) | — |

**Заглушки и ограничения**
- `STN_PRELOAD_DIR` — dev-переменная для демо и тестов, не продуктовая функция.
- Не распознаются: относительные изменения («увеличить на 10%» → «Требует проверки»), суммы только прописью, содержимое отсутствующих приложений, гомоглифы в номерах (кириллическая «С» вместо латинской «C»).
- Поэтапные сроки не поддерживаются: если в одном предложении несколько сроков поставки, правило может взять только первый.
- Статус подписания читается только из строки «Статус: …». Если её нет, статус неизвестен и документ получает «Требует проверки».
- Только TXT. Подписи не проверяются: система опирается на текст документа.
- Надписи внутри поля загрузки («Upload», «200MB per file») — встроенные строки Streamlit, они на английском.

## 5. Масштабирование до 100 000 документов с правами доступа

_Черновик, финализируется на итерации 8._

- **Загрузка.** Очередь и воркеры разбирают документы один раз. Идемпотентность обеспечивается хэшем содержимого.
- **Хранение.** PostgreSQL: результаты анализа в JSONB, индексы по номеру договора и поставщику, полнотекстовый поиск. Исходные тексты — в объектном хранилище.
- **Пересчёт.** Резолвер — чистая функция по группе документов одного договора. Новый документ пересчитывает только свою группу.
- **Доступ.** SSO (OIDC), роли и атрибуты (подразделение, категория закупок), Row-Level Security в БД.
  - Права выдаются на уровне группы договора, чтобы действующие значения не раскрывали содержимое недоступных допсоглашений.
  - Просмотр цитат проходит ту же проверку прав.
  - Просмотры записываются в журнал аудита.
- **Качество.** Мониторинг доли «Требует проверки», очередь ручной проверки, регрессионный размеченный корпус.

## 6. Три следующих улучшения

_Черновик, финализируется на итерации 8._

1. **Больше формулировок.** Поэтапные сроки, цена в валюте или без НДС, суммы прописью. Нужен размеченный корпус для регрессионных тестов.
2. **Очередь ручного подтверждения.** Значения «Требует проверки» подтверждаются вручную, решения сохраняются и становятся данными для улучшения правил.
3. **Новые источники и выгрузка.** Импорт PDF/DOCX и статусов подписания из ЭДО; экспорт в Excel и напоминания о приближающихся сроках поставки.
