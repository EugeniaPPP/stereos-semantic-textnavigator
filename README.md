# Semantic TextNavigator

Прототип показывает сумму и срок поставки, действующие на выбранную дату. Источник — TXT-документы: договоры, допсоглашения, проекты изменений и письма. У каждого значения есть точная цитата и переход к исходному абзацу.

**Демо:** https://stereos-textnavigator.streamlit.app — загрузите файлы из [`documents/`](documents/).
**Документы:** [требования](docs/PRD.md), [задание](docs/TASK.md), [архитектура](docs/ARCHITECTURE.md), [план и журнал](docs/PLAN.md), [отчёт по вайбкодингу](VIBECODING_REPORT.md), [прежняя подробная версия README](old_README.md).

```bash
python3.12 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/streamlit run app.py      # затем загрузите файлы из documents/
.venv/bin/pytest                    # 288 тестов
```

## Для кого

Прототип сделан для специалиста по закупкам, который сверяет условия поставок. Ему нужно быстро увидеть действующие сумму и срок на конкретную дату и проверить, откуда взялось каждое значение. При этом не нужно перечитывать все документы и легко не перепутать письмо или проект с согласованным изменением.

## Пять вопросов клиенту

1. Если стоимость задана в приложении или спецификации (как в STN-103), нужно ли загружать приложения и считать стоимость по ним?
2. Кто решает судьбу позиций «Требует проверки» и какой приоритет у конфликтующих изменений, например у двух ДС с одной датой вступления в силу?
3. Откуда брать достоверный статус подписания: из текста документа, из ЭДО или из учётной системы?
4. Какие условия, кроме суммы и срока, критичны: поэтапные сроки, неустойка, оплата, валюта и НДС?
5. Откуда и в каком объёме приходят документы (СЭД, почта, сканы) и нужна ли выгрузка результата (Excel, 1С)?

## Допущения

- Статус подписания и даты в тексте документа достоверны; подписи не проверяются.
- Формат — как в примерах:
  - строки «Статус:» и «Дата:»;
  - даты вида «ДД.ММ.ГГГГ» или «30 апреля 2026»;
  - суммы цифрами в рублях;
  - один абзац — одна строка.
- У договора одна общая стоимость и один срок поставки. Номер договора уникален и одинаково записан во всех документах.
- Условия меняет только допсоглашение, подписанное обеими сторонами и вступившее в силу к дате проверки (включительно). Письма и проекты — это предложения.
- Имена файлов и порядок загрузки на результат не влияют.

## Две метрики

1. **Доля неверных «уверенных» значений.** Считаются случаи на размеченном наборе, когда показано значение (а не «Нет данных» или «Требует проверки») и оно расходится с эталоном. Цель — 0%. Это метрика доверия.
2. **Покрытие** — доля договоров, у которых сумма и срок определены без «Требует проверки». Показывает экономию ручной работы. Растить её можно только без ухудшения первой метрики.

## Архитектура

```
TXT → разбор: абзацы и предложения с точными офсетами
    → извлечение по правилам: тип, номер, подпись, даты; сумма и срок с цитатой
    → связывание документов по номеру договора
    → статусы на дату проверки и действующие значения
    → Streamlit: таблица, фильтр, детали, исходный текст с подсветкой
```

Ядро — чистые детерминированные функции на Python, без LLM и без Streamlit. Новое извлекаемое поле — это запись в реестре правил, без переработки движка. Интерфейс пересчитывает всё при каждом изменении файлов или даты. Подробности, полный список решений и ограничений — в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Три ключевых технических решения

| Решение | Компромисс |
|---|---|
| **Правила вместо LLM.** Регулярные выражения и контекстные правила работают на уровне предложения. Слова-исключения (аванс, лимит, оплата, приёмка) проверяются в тексте до значения. Результат детерминирован, проверяем, бесплатен и работает офлайн | Незнакомая формулировка даёт «Требует проверки» или «Нет данных», а не значение. Каждую новую формулировку нужно добавлять правилом и тестом |
| **Консервативное разрешение.** Изменение применяется, только если ДС подписано обеими сторонами и вступило в силу. «Требует проверки» получают: противоречие типа и статуса подписи, нераспознанное изменение суммы или срока, разные значения с одной датой вступления. Подписанные, но не вступившие в силу ДС отделены от несогласованных предложений | Точность (метрика 1) получена ценой покрытия (метрика 2): ручных проверок больше |
| **Доказательность.** Каждое значение хранит точный фрагмент текста и его место — файл, абзац, пункт. Идентичность документа — хэш содержимого, а не имя файла | Модель «абзац = строка» не выдержит файлов с жёсткими переносами. Таблица статичная: всё читается целиком, но сортировки нет |

## 100 000 документов и права доступа

Правила и резолвер переносятся без изменений: разбор занимает около 0,2 мс на документ, а резолвер работает на группе документов одного договора. Меняется всё вокруг них.

- **Загрузка.** Очередь и воркеры разбирают каждый документ один раз; хэш содержимого делает загрузку идемпотентной.
- **Хранение.** PostgreSQL: результаты анализа, связи с договорами, индексы, полнотекстовый поиск. Исходные файлы — в объектном хранилище.
- **Пересчёт.** Новый документ пересчитывает только свою группу договора. Результаты на дату кэшируются, таблица отдаётся с серверной пагинацией.
- **Права доступа.**
  - Вход через SSO, роли и атрибуты: подразделение, категория закупок, поставщик.
  - Права выдаются на группу договора, а не на файл: иначе действующее значение раскрыло бы содержимое недоступного допсоглашения.
  - Права проверяются в БД (Row-Level Security) и API; просмотр цитат проходит ту же проверку; просмотры попадают в журнал аудита.
- **Интерфейс.** Streamlit годится для прототипа. Для такого масштаба нужно веб-приложение поверх API.

## Следующие улучшения (по приоритету)

1. **Регрессионный корпус и новые формулировки.** Без размеченного корпуса нельзя измерить обе метрики и безопасно расширять правила: поэтапные сроки, цену в валюте или без НДС, суммы прописью, ссылки на приложения.
2. **Ручное подтверждение.** Специалист подтверждает или исправляет значение «Требует проверки» прямо в деталях договора, решение сохраняется. Так консервативность перестаёт быть тупиком и даёт материал для новых правил.
3. **Новые источники и выгрузка.** Импорт PDF/DOCX и статусов подписания из ЭДО, экспорт в Excel, напоминания о сроках поставки и о предложениях, ожидающих решения.
